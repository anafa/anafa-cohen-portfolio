## Current structure

- `index.html` — real markup for header, hero, and about sections. Text content is left empty in HTML (e.g. `<h1 id="hero-name"></h1>`) and filled in at runtime by `js/main.js` from `content/cv.json` — markup itself stays content-agnostic. Static `<title>`/`<meta description>` are hardcoded with real copy (good for SEO/screen readers before JS runs). Includes a `<noscript>` fallback pointing to the contact email.
- `css/styles.css` — full "Night Field" design system from `docs/design.md`: CSS custom properties for the palette/type tokens, mobile-first layout (single column below 768px, two-column hero/about above), a faint scan-grid body background (subtle radar/satellite-frame texture), focus-visible styles, skip link, and `prefers-reduced-motion` handling for all corner/reveal animations.
  - **Bounding-box corner motif** (`.corner` + `.corner-tl/tr/bl/br`) is reserved for exactly two structural uses — the `.hero-frame` (large scale, 40px/3px) and `.section-heading` (small scale, 22px/2px) — deliberately *not* applied to every photo/card. First pass (Part 5 v1) sprinkled small corners on individual photo frames and it read as decorative clutter rather than a signature element; user feedback ("didn't like the design... too sparse... corner motif") led to reworking it as a structural device instead: the whole hero (photo + headline + CTA) sits inside one `.hero-frame` with corners at its edges. Keep this restraint going forward — don't add corners to every image without a structural reason. **Note:** the hero frame originally also had a `.frame-tag` annotation label (`SUBJECT: ENGINEER · CONF 0.99`) overlapping its top edge; removed per explicit user request — `.frame-tag` no longer exists in CSS or HTML. Don't re-add it without being asked.
  - **About "readout panel"** (`.readout`/`.readout-row`) replaced an earlier grid-of-stat-cards pattern (felt like a generic SaaS dashboard cliché). It's a single bordered label/value list, monospace values in amber — same visual language elsewhere on the page. **Two rows now, in this order: Education, then Focus Areas** — all the plain inline label/value row (`.readout-row`). History: originally 3 rows (Experience, Focus Areas, Education); a "Core Capabilities" row briefly existed too (first as boxed tag chips via a `.readout-row--wrap` modifier, then as a plain dot-separated line) but got merged into the Skills section instead (renamed **Core Capabilities**, see below) — `.readout-row--wrap` no longer exists in CSS. Don't re-add an Experience row or reorder these two without being asked.
  - **Core Capabilities section** (`id="core-capabilities"`, class `.skills` — CSS class intentionally left as-is, it's an internal style hook not tied to the visible heading text) sits directly after About, before Experience. This *is* the renamed former "Skills" section — same `.skills-group`/`.skills-tags`/`.skill-tag` markup and styling (amber-outlined monospace chips grouped by category), just relabeled and repositioned per user request. `renderSkills()` in `main.js` targets `#core-capabilities-groups` (renamed from `#skills-groups`); the function name itself wasn't renamed (cosmetic, low priority) but its DOM targets and the rendered heading text were.
  - **Experience cards** (`.role-list`/`.role-card`) are three flex children per role on desktop (≥768px): `.role-logo`, `.role-content` (title/company/dates/bullets, flexible middle), `.role-gallery` (a browsable project-image carousel). On mobile all three stack vertically.
    - `.role-logo` is a fixed **9.75rem × 4.23rem rectangle** (not square — real wordmark logos are wide, a square box would waste most of it; scaled up 1.3× from an initial 7.5rem × 3.25rem per user request) with a solid **ivory background** (`var(--color-ivory)`) behind every logo, real or placeholder. This is deliberate: the actual company logo files are a mix of dark-background (Airis, Pixellot) and light-background (Taranis, PlanetWatchers) brand assets with their own background baked in (all fully opaque PNGs, no transparency — checked with PIL before deciding), so a uniform light "mount" behind all four is what makes them read as a consistent set rather than four differently-treated images. `object-fit: contain` on `.logo-img` preserves each logo's own aspect ratio without distortion or cropping. The placeholder state (`.logo-placeholder`) drops the ivory fill for a transparent dashed-border box instead, so an unfilled slot still reads as "pending," not as a real (blank) logo.
    - `.role-gallery`'s size is **not a fixed CSS value** — `syncGalleryHeights()` in `main.js` measures every `.role-content`'s rendered `offsetHeight` at desktop widths, takes the tallest one, then **multiplies it by 0.75** (`maxHeight *= 0.75`) before applying it to every `.gallery-viewport` — originally matched 1:1 to "the same size as the largest you find," then the user found that too big and asked for 0.75× the matched size specifically. Still guarantees all four galleries are equal and content-proportional, just smaller than a literal 1:1 match. Re-measured on `document.fonts.ready` and on debounced window resize; cleared back to a CSS `aspect-ratio: 4/3` fallback below 768px where cards stack and this matching doesn't apply. The desktop column sizing (`.role-gallery { flex: 1 1 34%; min-width: 19.5rem; }`, `.role-content { flex: 1 1 56%; }`) and the prev/next arrow buttons (`1.69rem` circles, `0.83rem` glyph, `0.45rem` inset — down from `2.25rem`/`1.1rem`/`0.6rem`) were scaled by the same 0.75× alongside the height, so the whole gallery (box + controls) shrank as one proportional unit rather than just the image area. If you touch role-card text, breakpoints, or the gallery size again, keep this ratio in mind rather than re-deriving magic numbers from scratch.
    - **Arrow positioning**: `.gallery-prev`/`.gallery-next` (`position: absolute; top: 50%`) are appended to `.gallery-viewport` (the image box itself, now `position: relative`), *not* to `.role-gallery` (the outer wrapper that also contains `.gallery-dots` below the image). Get this wrong and `top: 50%` centers the arrows against image+dots combined instead of just the image — harmless when the image dominates the total height, but visibly wrong once the image shrinks relative to the dots row (exactly what happened after the 0.75× resize: arrows stayed where the *old, taller* image's center used to be). `.gallery-dots` stays a child of `wrap` (`.role-gallery`) since it belongs below the image, not inside it.
    - **Dots sizing**: `.gallery-dots`/`.gallery-dot` (gap, `margin-top`, dot diameter) are scaled by the same 0.75× as everything else in the gallery (`6px` dots, `0.375rem` gap, `0.5625rem` margin-top — down from `8px`/`0.5rem`/`0.75rem`). This was a real inconsistency, not a phantom bug: the first 0.75× resize pass scaled the gallery box, JS-computed height, and arrows, but left the dots' own sizing untouched — so relative to the now-smaller image, the dots sat with disproportionately large spacing/size, looking visually disconnected from it. Horizontal centering itself (`justify-content: center` on a full-width flex container matching `.gallery-viewport`'s width) was already structurally correct — the fix here was proportional sizing, not an actual centering bug. If the gallery size changes again, remember to scale the dots along with everything else, not just the box/arrows.
    - Both `.role-logo`'s placeholder and the gallery's empty-state (`.gallery-placeholder`) reuse the dashed-border placeholder look from the hero photo, deliberately *without* corner brackets — same restraint as above. The gallery is a real carousel component (`buildGallery()` in `main.js`): prev/next buttons + dot navigation only render when a role has 2+ images in `cv.roles[].gallery`; with 0 or 1 (currently just Airis-Labs — empty array), it shows a single "Project images coming soon" slide with no dead/disabled nav controls cluttering the UI.
  - **Freelance intro** (`.freelance-intro`, `<p id="freelance-statement">`) is *not* a `<section>` — it's a short, unheaded, centered paragraph sitting between the hero and About, styled in the teal accent/display font (echoes the hero tagline). No landmark/heading because there deliberately isn't one — don't wrap it in `<section>` without adding an accessible name.

## Tooling

- No Node.js/npm — plain HTML/CSS/JS, no build step.
- **Local dev server serves `frontend/` as the site root** (`http://localhost:8000/`, not `/frontend/`) — this changed for Netlify deployment-readiness (see below). Before starting the python server, `scripts/start.sh`/`start.ps1` copy `content/cv.json` → `frontend/content/cv.json` (gitignored — `content/cv.json` at the project root is still the single source of truth, this copy is a disposable build/dev artifact regenerated on every `scripts/start`). `main.js` fetches `content/cv.json` (relative, no `../`), which now resolves identically whether `frontend/` is served directly (local dev, and Netlify) or nested under a parent (not used anymore, but the pattern generalizes). **If you add new content files under `content/`, they won't be visible to the site until the copy step also copies them** — currently only `cv.json` is copied; extend the `cp`/`Copy-Item` line in both start scripts and in `netlify.toml`'s build command if that changes.
- **Netlify deployment**: `netlify.toml` at the repo root sets `publish = "frontend"` and a `build.command` that does the same `content/cv.json` copy the local dev scripts do, so the deployed site is self-contained the same way. No Node/build tooling involved — the "build command" is just a file copy.
- **Cache-busting**: `css/styles.css` and `js/main.js` are loaded via `<link>`/`<script>` tags in `index.html` with a manual query string, bumped independently per file when it actually changes — **currently `styles.css?v=6`, `main.js?v=6`**. `content/cv.json` fetches with `{ cache: "no-store" }` in `main.js`. Bump the version on both tags whenever a CSS/JS change doesn't seem to show up before spending time re-debugging code that's probably already correct — cheap insurance, kept from the debugging saga below even though caching turned out not to be the actual cause that time.
  - **Placeholder-visibility bug, full saga — never actually root-caused; the hero photo's "Photo coming soon" placeholder is now permanently disabled by user request, not fixed.** User reported a "Photo coming soon" box still visible (stacked right below the real headshot), and separately the same for role-logo "Logo" placeholders. Two fix attempts, each verified correct by every static check available, neither visibly resolved it for the user:
    1. `element.hidden = true/false` + a CSS `[hidden] { display: none !important; }` override (to beat `.photo-placeholder { display: flex; }`, an author rule that otherwise always wins over the non-important default `[hidden]` rule). Verified: no duplicate IDs, ID string byte-identical between HTML and `getElementById()`, exactly one `!important` display rule in the whole CSS file, JS a straight-line block with no way to skip the hide call, served bytes identical to source. Still reportedly visible after a hard refresh, and *still* visible after a cache-busting version bump that should have made a stale cache structurally impossible — which retroactively disproved the caching diagnosis too.
    2. Rewrote to avoid the CSS cascade entirely: `renderHero()` called `placeholder.remove()` instead of toggling `.hidden`, `buildLogo()` was rewritten to construct only the needed element (real `<img>` or placeholder `<div>`, never both). This should be bulletproof — an element removed from the DOM cannot be rendered by any CSS rule, full stop. **Still reported as not fixed.**
    - Given a `.remove()`'d element being unfixable by definition, at this point the mismatch between "verified correct in every way I can check" and "user still sees it" was never resolved or explained. **Per explicit user instruction**, the hero placeholder's HTML is now wrapped in `<!-- -->` (inert — the browser's parser converts it to a Comment node before any JS or CSS ever runs, so this doesn't depend on `.remove()`, `hidden`, or any cascade behavior at all) and every reference to `#hero-photo-placeholder` was deleted from `renderHero()` in `main.js` (leaving it would throw on `getElementById(...).remove()` returning `null`). The equivalent `.logo-placeholder`/"Logo" case for company logos was **not** touched in this pass — same bug pattern, not yet addressed the same way; ask the user before doing so if it comes up again, don't assume the same treatment is wanted without confirming.
    - **If a similarly "impossible" persistent-bug report comes up again**: don't keep proposing fix variants blind. Every code-level check available was exhausted here (byte diffs of served content, `!important` audits, `.remove()` — categorically not a CSS problem) without resolving the mismatch. Ask for something that bypasses static analysis entirely much earlier — a screenshot came eventually, but DevTools inspection (checking the actual computed style / whether the element is even in the live DOM) or a completely different browser/machine would have been more diagnostic and should be reached for sooner next time.
    - **Resolution, finally**: had the user check View Source (Ctrl+U) directly — their browser's view-source showed the *old, pre-comment* markup, while `curl` hitting the exact same URL from this machine, at the exact same time, correctly showed the commented-out version. That's the proof it was never a code problem at all: the server was verifiably correct the whole time, something local to the user's regular browser (cache, extension, or possibly security/antivirus software doing HTTP interception) was serving stale content in a way that survived hard refresh, cache-busted URLs, and even a manual "clear cached images and files" + full browser restart. **Confirmed fixed in an incognito/private window** — that's the user's working setup now for reviewing this site; regular-window caching remains unexplained and unresolved, but is a local browser environment issue, not a project bug. Worth remembering: if a future "I did X and it's still broken" report doesn't budge across several genuinely-should-have-worked fixes, suspect the user's browser/environment before assuming the code is still wrong — an incognito-window test is cheap and highly diagnostic, reach for it earlier next time.
- **Known Git Bash gotcha (fixed, root cause)**: on this Windows/Git Bash setup, MSYS assigns its own *virtual* PID numbers to processes, separate from the real Windows PID (visible as `ps`'s `WINPID` column) — and those virtual PIDs are only valid within the bash session that allocated them. A PID captured by `$!` in one `start.sh` invocation can refer to a different (or no) process by the time a later `stop.sh` invocation (a fresh bash session, e.g. a new tool call) tries to `kill` it — the server leaks silently, `stop.sh` reports success either way. (An earlier, incomplete fix suspected `nohup`'s wrapper process as the sole cause; that was real but not the whole story — the deeper issue persisted even without `nohup`.) Fixed properly by having `start.sh` resolve and persist the real Windows PID (`ps -p $! | tail -1 | awk '{print $4}'`) and having `stop.sh` use `taskkill //F //PID` instead of bash's `kill` — both operate on the stable, session-independent Windows PID. Verified clean across separate shell invocations and repeated start/stop cycles via `netstat`. `start.ps1`/`stop.ps1` were never affected — PowerShell's `Start-Process`/`Stop-Process` use real Windows PIDs natively.

## Conventions (established, keep enforcing)

- **`[hidden] { display: none !important; }`** is declared once near the top of `css/styles.css` (Reset section) and must stay. Root cause it fixes: several placeholder elements (`.photo-placeholder` and friends) set `display: flex` for centering; as an author rule, that silently wins over the browser's default `[hidden] { display: none }` regardless of specificity, because author styles always beat user-agent styles. Without this override, `element.hidden = true` in `main.js` (used to hide the hero/logo placeholders once a real image loads) had no visual effect — real bug, found and fixed after the user reported leftover "Photo coming soon"/"Logo" text still showing. If you add any new placeholder-style element with an explicit `display` value that gets toggled via the `hidden` property/attribute, this global rule already covers it — don't add a per-element fix instead, and don't remove this rule.
- Real content only — no lorem ipsum, no invented CV details. Every piece of dynamic text traces back to a specific `content/cv.json` field.
- Every `<img>` has descriptive alt text; the hero photo placeholder has no `<img>` at all when unset (avoids empty/misleading alt).
- Respect `prefers-reduced-motion` for any animation — established pattern: default (no-preference) styles live inside `@media (prefers-reduced-motion: no-preference)`, so reduced-motion users get the end state with no transition at all, not just a faster one.
- Mobile-first responsive layout: base CSS is the mobile layout, `@media (min-width: 768px)` layers on the desktop layout.
- Hero CTA links to `#contact` (in-page anchor) now that the Contact section exists — it's a plain static `href` in the HTML, not JS-set.

Update this file whenever the structure above changes or new conventions are established.
